# v0.4 릴리즈 런북 (Phase 1 운영 적용)

> - 대상: `feat/phase1` → `main` 병합 때 운영 Supabase와 Vercel에 적용하는 사람(프로젝트 관리자)
> - 원칙: §12-Q21. 마이그레이션은 로컬과 `npm run test:rls:ci`(운영 재현 시나리오 `prod_replay`)로 검증을 마쳤고, 운영 적용은 사람이 SQL Editor에서 합니다. MCP로는 적용하지 않습니다.
> - 순서: **① 추가형 마이그레이션 → ② 앱 배포 → ③ 권한 회수 마이그레이션.** 새 앱은 ①만 적용된 DB와 ①+③ DB 모두에서 동작하고, 이전 앱은 ①만 적용된 DB에서 동작합니다.
> - 각 SQL 파일은 SQL Editor에서 `BEGIN;` + 파일 내용 + `COMMIT;`으로 감싸 실행합니다. 자기 검증 NOTICE가 기대값과 다르면 `ROLLBACK;`하고 멈춥니다.
> - ⚠️ **SQL Editor 붙여넣기는 줄바꿈이 CRLF로 바뀝니다**(Windows, B39). 그래서 처음 시도한 ① 묶음이 00012에서 `KS X 1001 한글 목록이 2,350자가 아님 (2398자)`로 실패했습니다(트랜잭션이라 운영은 그대로). 00012와 콘텐츠 seed를 CRLF에 안전하게 고쳤으니, 파일을 하나씩 감싸 붙이지 말고 **`release-sql` 묶음 파일**을 씁니다: `node scripts/release/build-release-sql.mjs` → 저장소의 `release-sql/`(git 제외)에 `1_먼저실행.sql`(① 11개) · `2_두번째실행.sql`(③ 00005·08·11·13·15 + 콘텐츠 seed) · `3_선택.sql`(00009). 각 파일 안에 `BEGIN;`/`COMMIT;`이 있어 파일 전체를 그대로 붙여 실행하고, 하나라도 실패하면 그 파일 전체가 되돌려집니다. 이 묶음을 CRLF로 바꿔 운영 재현 DB에 그대로 적용하는 리허설: `RLS_CRLF=1 RLS_SKIP_NEWDEFAULT=1 npm run test:rls:ci`(점검 CR-1~4: `\r` 0, LF 적용 결과와 같음)

작업이 끝날 때마다 이 문서에 단계를 추가합니다. 체크박스는 운영 적용 당일에 채웁니다. Phase 3 병합(릴리즈 묶음 `v0.4-phase3`)은 맨 아래 "Phase 3 병합" 절입니다.

#### 00019 확인 (B11 후속, Q25)

- 적용 전 기록(읽기 전용, 참고값): 황금키로 완료한 행 수와, 그 완료 시각에 받은 것으로 보이는 뱃지 수. 이 파일은 이미 받은 뱃지를 바꾸지 않으므로 기록만 합니다
  ```sql
  select count(*) from public.user_progress where status = 'completed' and used_golden_key;
  select b.badge_type, count(*) from public.user_badges b
    join public.user_progress p on p.user_id = b.user_id and p.used_golden_key and p.status = 'completed'
   where abs(extract(epoch from (b.earned_at - p.completed_at))) < 5
   group by 1 order by 1;
  ```
- 적용 후
  ```sql
  select public.decide_new_badges('{}', 1, true, true, 0, true, true);    -- {} (황금키 완료는 뱃지 없음)
  select public.decide_new_badges('{}', 1, false, false, 0, false, false); -- {first_code,hint_master}
  select p.proname, has_function_privilege('anon', p.oid, 'EXECUTE') anon, has_function_privilege('authenticated', p.oid, 'EXECUTE') auth,
         has_function_privilege('service_role', p.oid, 'EXECUTE') svc
    from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'public' and p.proname in ('decide_new_badges', 'complete_quest');   -- 두 줄 모두 f, f, t
  ```
- ⚠️ ② 뒤 "00006 백필 재실행"은 런북의 UPDATE 한 문장만 실행합니다. 00006 **파일 전체**를 다시 실행하면 두 함수가 00006 정의로 돌아가므로, 그랬다면 00019를 다시 적용합니다

## 게시판 신고 처리 (운영, P1-18)

```sql
-- 1. 최근 신고 (대상별)
select r.target_type, r.target_id, count(*) as reports, array_agg(distinct r.reason) as reasons,
       min(r.created_at) as first_at, max(r.created_at) as last_at,
       coalesce(p.is_hidden, c.is_hidden) as hidden,
       left(coalesce(p.title || ' / ' || p.content, c.content), 80) as preview
  from public.board_reports r
  left join public.board_posts p on r.target_type = 'post' and p.id = r.target_id
  left join public.board_comments c on r.target_type = 'comment' and c.id = r.target_id
 group by 1, 2, p.is_hidden, c.is_hidden, p.title, p.content, c.content
 order by last_at desc limit 50;

-- 2. 자동으로 숨겨진 글·댓글 (신고자 3명 이상)
select 'post' as t, id, user_id, left(title || ' / ' || content, 80), hidden_at from public.board_posts where is_hidden
union all
select 'comment', id, user_id, left(content, 80), hidden_at from public.board_comments where is_hidden
order by hidden_at desc;

-- 3-a. 문제없는 글이면 숨김 해제 (신고 기록을 지우면 다시 3명이 신고해야 숨겨짐. 남겨 두면 다음 신고 1건에 다시 숨겨짐)
begin;
update public.board_posts set is_hidden = false, hidden_at = null where id = '<글 id>';
delete from public.board_reports where target_type = 'post' and target_id = '<글 id>';
commit;
-- 댓글은 board_comments · target_type = 'comment'

-- 3-b. 문제가 있으면 삭제 (글을 지우면 댓글도 함께 지워짐. 신고 기록은 남김)
delete from public.board_posts where id = '<글 id>';
delete from public.board_comments where id = '<댓글 id>';

-- 4. 여러 번 신고된 작성자 (같은 아이가 반복하는지)
select target_user_id, count(*) as reports, count(distinct target_id) as targets, max(created_at) as last_at
  from public.board_reports where target_user_id is not null
 group by 1 order by 2 desc limit 20;
```

## 튜터 한도·남용 기록 (운영, P1-19)

튜터 API(`/api/tutor`, `/api/tutor/stream`)는 사용자마다 요청 유형별로 **분당 / 하루(KST 자정 기준)** 한도를 DB(`api_rate_limits`, `consume_rate_limit`)로 셉니다. 넘으면 429 + `Retry-After`이고 아이에게는 "파이뱀 선생님이 잠깐 쉬고 있어요. N초 뒤에 다시 물어봐요!"(하루 한도는 "내일 다시")가 기준 문구입니다(지금 퀘스트 화면은 기존 실패 문구를 보여 주고 힌트 횟수는 되돌림). 서버 무료 티어 키(Gemini)는 프로젝트 전체가 함께 쓰는 한도라 한 사람이 다 쓰지 못하게 하는 장치입니다.

| env (Vercel, 서버 전용) | 기본값 (분당/하루) | 요청 유형 | 근거 (정상 학습 속도) |
|---|---|---|---|
| `TUTOR_LIMIT_INTRO` | `8/60` | 퀘스트 소개 `quest_intro` | 퀘스트에 들어갈 때 1번 |
| `TUTOR_LIMIT_HINT` | `6/60` | 힌트 `hint_generator` | 단계마다 최대 3번(프로젝트는 단계마다 다시 3번) |
| `TUTOR_LIMIT_FEEDBACK` | `12/200` | 실행 결과 피드백 `code_feedback` | 실행마다 1번. 5초마다 실행해도 통과 |
| `TUTOR_LIMIT_ENCOURAGEMENT` | `4/40` | 완료 격려 `encouragement` | 완료마다 1번 |
| `TUTOR_LIMIT_GUIDE` | `6/40` | 프로젝트 단계 안내 `project_guide` | 단계에 들어갈 때 1번 |
| `TUTOR_LIMIT_SUMMARY` | `3/20` | 스테이지 정리 `stage_summary` | 스테이지 클리어 때 1번 |
| `TUTOR_LIMIT_OWN_KEY_MULTIPLIER` | `2/5` | 본인 API 키 사용자의 배수 | LLM 비용은 본인 부담이라 하루는 ×5, 분당은 서버 부하용이라 ×2 |

- 형식이 틀린 값은 무시하고 기본값을 씁니다(로그 `[tutor] TUTOR_LIMIT_… 형식이 잘못됨`). 바꾼 뒤에는 재배포해야 적용됩니다. 캐시 적중(`quest_intro`·`stage_summary`)도 한도에 셉니다(캐시가 인스턴스마다 따로라 적중 여부로 한도가 달라지지 않게).
- 한도 DB 호출이 실패하면 **통과시킵니다**(fail-open, 튜터를 멈추지 않음). 로그 `[tutor] consume_rate_limit 실패` + Sentry `area:tutor op:rate_limit`.
- 수업 시간에 정상 사용이 막힌다는 제보가 있으면 아래 2번 쿼리로 확인하고 env를 올립니다. 한도를 끄는 스위치는 없습니다(아주 큰 값, 예: `1000/10000`).

**서버 Gemini 키 전역 예산 (P1-22)**: Gemini 한도는 사용자별이 아니라 Google 프로젝트 전체에 걸리므로, 서버 키로 Gemini를 부르기 직전에 모든 사용자의 합계를 한 번 더 셉니다(`api_global_rate_limits`, `consume_global_rate_limit`, 버킷 `tutor:gemini:global`). 캐시 적중과 학생 본인 키 호출은 세지 않고, 본인 키가 실패해 무료 티어로 폴백할 때는 셉니다. 넘으면 Gemini를 부르지 않고 저장된 답변을 보냅니다(429가 아님 — 아이에게는 평소의 저장된 답변).

| env (Vercel, 서버 전용) | 기본값 (분당/하루) | 근거 |
|---|---|---|
| `TUTOR_GLOBAL_LIMIT_GEMINI` | `10/500` | Gemini 무료 티어 수준(공개 문서에 수치가 없어 프로젝트의 AI Studio rate limit 화면 값으로 맞춤). 무료 티어를 넘는 요청은 어차피 Google이 429로 거절하므로 무료 티어에서는 잃는 것이 없고, 결제를 켠 프로젝트에서는 하루 비용 상한 |

- 예산을 넘으면 분 창마다 처음 한 번 로그 `[tutor] 서버 gemini 키 전역 예산 초과 (minute|day, …)` + Sentry 경고 `tutor server key budget exhausted`(`op:server_key_budget`). 하루 예산(`day`)이 자주 보이면 사용자가 늘어난 것이므로 AI Studio에서 실제 한도를 다시 확인하고 env를 올리거나 결제(유료 티어)를 검토합니다.
- 하루 창은 KST 자정 기준이고 Google 무료 티어는 태평양 시간 자정에 초기화됩니다(겨울 기준 KST 17시). 그래서 하루 예산을 Google 한도와 똑같이 두면 경계 근처에서 몇 시간 어긋날 수 있어 조금 낮게 둡니다.
- 예산 DB 호출이 실패하면 **통과시킵니다**(fail-open). 로그 `[tutor] consume_global_rate_limit 실패` + Sentry `op:server_key_budget`.
- 오늘 사용량: `select minute_count, day, day_count, day_denied, updated_at from public.api_global_rate_limits where bucket = 'tutor:gemini:global';` / 잘못 막혔을 때 풀기: `delete from public.api_global_rate_limits where bucket = 'tutor:gemini:global';`

**비정상 요청 기록**: Vercel 로그에서 `[tutor-abuse]`로 찾습니다. 한 줄이 JSON `{"event":"tutor_abuse","level","reason","kind","user":<사용자 해시 16자>, …}`이고 학생 코드·출력·질문은 들어 있지 않습니다.

| reason | 뜻 | 수준 |
|---|---|---|
| `rate_limited` | 한도 초과 (`scope` minute/day, `denied_minute`·`denied_today`) | info. 같은 분 창에 5번 이상 또는 하루 100번 이상이면 warning |
| `invalid_json`·`invalid_type`·`missing_quest_id`·`invalid_hint_level`·`missing_execution_result` | 우리 화면은 보내지 않는 형식 (직접 만든 요청) | warning |
| `body_too_large` | 본문 64KB 초과 (413, 읽지 않음) | warning |
| `quest_not_found` | 없는 퀘스트 id (`quest_id`는 UUID일 때만 남김) | warning |
| `input_too_long` | 길이 제한을 넘어 잘라서 처리 (`fields`에 필드 이름만) | info |
| `stage_locked` | 잠긴 스테이지의 퀘스트에 튜터 호출 (403으로 막음, B38. 퀘스트 화면도 월드맵으로 돌려보냄) | warning |

- warning은 Sentry 메시지 `tutor abuse: <reason>`으로도 갑니다(사유별 한 이슈, 인스턴스마다 10분 3번까지. 사용자 해시는 Sentry에 보내지 않음 — P1-16 최소 수집). 한 사유가 갑자기 늘면 Vercel 로그에서 같은 시간대의 `user` 해시를 봅니다.

```sql
-- 1. 로그의 사용자 해시 → 사용자 (해시 = sha256(user id) 앞 16자)
select id, created_at, last_login_at from public.users
 where left(encode(sha256(convert_to(id::text, 'UTF8')), 'hex'), 16) = '<해시>';

-- 2. 오늘(KST) 한도에 걸린 사용자·유형 (카운터는 최근 2일치만 남음)
select left(encode(sha256(convert_to(user_id::text, 'UTF8')), 'hex'), 16) as user_hash, bucket,
       day_count, day_denied, updated_at
  from public.api_rate_limits
 where day = public.kst_today() and day_denied > 0
 order by day_denied desc limit 20;

-- 3. 오늘 많이 쓴 사용자 (정상 사용량 확인, 한도 조정 근거)
select bucket, count(*) as users, max(day_count) as max_count,
       percentile_cont(0.9) within group (order by day_count) as p90
  from public.api_rate_limits where day = public.kst_today() group by 1 order by 1;

-- 4. 특정 사용자의 오늘 한도 풀기 (잘못 막혔을 때)
delete from public.api_rate_limits where user_id = '<id>' and bucket = 'tutor:<유형>';
```

## 관리자 role 설정 (운영, B37)

새 앱은 관리자를 `app_metadata.role = 'admin'`으로 판별하고(`src/lib/admin.ts`), 이행 기간에만 `ADMIN_EMAIL`과 같은 **확인된** 이메일을 폴백으로 인정합니다. `app_metadata`(DB `raw_app_meta_data`)는 service_role·postgres만 바꿀 수 있습니다. `user_metadata`(`raw_user_meta_data`)는 사용자가 직접 바꿀 수 있으므로 **절대 여기에 role을 넣지 않습니다.** 이전 앱은 role을 보지 않으므로 ① 전이든 ② 뒤든 언제 해도 되고, 마이그레이션 파일은 없습니다. SQL Editor(postgres)에서 실행합니다.

```sql
-- 1. 확인 (읽기 전용): 관리자 계정 찾기 — Vercel env ADMIN_EMAIL 값으로
select u.id, u.email, u.email_confirmed_at is not null as email_confirmed,
       u.raw_app_meta_data ->> 'role' as role,
       array_agg(i.provider order by i.created_at) as identities, u.last_sign_in_at
  from auth.users u
  left join auth.identities i on i.user_id = u.id
 where lower(u.email) = lower('<ADMIN_EMAIL 값>')
 group by u.id;
-- 기대: 1행, email_confirmed = true, role = NULL(아직 설정 전). 2행 이상이거나 0행이면 멈추고 확인

-- 지금 role = admin 인 계정 전체 (설정 전에는 0행, 설정 뒤에는 의도한 계정만)
select id, email, raw_app_meta_data ->> 'role' as role, last_sign_in_at
  from auth.users where raw_app_meta_data ->> 'role' = 'admin';

-- 2. 설정: 1번에서 확인한 id 하나만
begin;
update auth.users
   set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) || '{"role":"admin"}'::jsonb
 where id = '<관리자 id>';
-- 기대: UPDATE 1. 아니면 rollback;
select id, email, raw_app_meta_data from auth.users where id = '<관리자 id>';
-- 기대: 기존 provider·providers 키가 그대로 있고 "role": "admin" 이 더해짐
commit;

-- 회수 (관리자를 바꾸거나 잘못 넣었을 때)
update auth.users set raw_app_meta_data = raw_app_meta_data - 'role' where id = '<id>';
```

- 앱은 요청마다 `auth.getUser()`로 Auth 서버에서 사용자를 새로 읽으므로 **다시 로그인하지 않아도 바로 반영**됩니다(브라우저 JWT의 `app_metadata`는 토큰 갱신 전까지 예전 값이지만 판별에 쓰지 않음).
- 확인: 관리자 계정으로 `/notice` → "공지 작성" 버튼이 보임. role만으로 되는지까지 보려면 로컬이나 Preview에서 `ADMIN_EMAIL`을 비우고 같은 계정으로 확인합니다.
- Kakao·Naver로 들어오는 관리자는 이메일이 없으므로(§2.8) role로만 관리자가 됩니다. id는 `select user_id from auth.identities where provider = 'kakao' and provider_id = '<회원번호>';`처럼 identity로 찾습니다.
- **폴백 제거 (다음 릴리즈)**: 위 설정과 확인을 마친 뒤 `src/lib/admin.ts`의 `TODO(B37)` 폴백과 `.env.example`·Vercel의 `ADMIN_EMAIL`을 지웁니다. 그 전에 2번의 "role = admin 계정 전체" 쿼리가 의도한 계정을 돌려주는지 다시 확인합니다.

## 보안 헤더·CSP (B27)

페이지 CSP는 `src/middleware.ts`, 그 밖의 헤더·Worker CSP·API CSP는 `next.config.ts`가 붙입니다(생성 로직은 `src/lib/security/csp.ts`).

- 동적 페이지(로그인 화면·공지·게시판·퀘스트·404): `script-src 'self' 'nonce-…' 'strict-dynamic'` — 요청마다 nonce
- 정적 페이지(랜딩 `/`만): `script-src 'self' 'unsafe-inline'` — 빌드 때 만든 HTML이라 nonce를 넣을 수 없음. 사용자 콘텐츠가 없고 CDN 캐시를 유지(§2.10)
- Pyodide Worker(`/workers/*.mjs`): `default-src 'none'; script-src 'self' 'wasm-unsafe-eval' <jsDelivr 314.0.7>; connect-src 'self' <jsDelivr 314.0.7>` — **항상 강제**(Report-Only로 바꾸지 않음. 바꾸면 Python → `Function` 우회가 열림)
- 운영에는 어디에도 `'unsafe-eval'`이 없음(개발 서버만)
- 배포 방식: **처음부터 강제**(Report-Only 단계 없음). 근거: 외부 스크립트·iframe이 없어 막힐 만한 출처가 Supabase·Sentry·jsDelivr뿐이고 로컬 `next start`에서 Chromium·Firefox 위반 0을 확인함. Report-Only는 막지 않으므로 그동안 보호가 없음. 대신 Preview에서 강제 상태로 먼저 확인하고, 문제가 생기면 아래 비상 전환을 씀

### Preview에서 (Production 승격 전)

1. [ ] 헤더 확인 (터미널, `<preview>`는 Preview 주소)
   ```bash
   curl -sI https://<preview>/ | grep -iE 'content-security|x-frame|x-content-type|referrer-policy|permissions-policy|strict-transport'
   curl -sI https://<preview>/notice | grep -i content-security          # 'nonce-…' 'strict-dynamic'
   curl -sI https://<preview>/workers/pyodide-worker.mjs | grep -i content-security   # default-src 'none' … 'wasm-unsafe-eval'
   curl -sI https://<preview>/api/notice | grep -i content-security      # default-src 'none'; frame-ancestors 'none'
   curl -sI https://<preview>/ https://<preview>/notice https://<preview>/workers/pyodide-worker.mjs | grep -c "'unsafe-eval'"   # 0
   ```
   - `/`·`/notice`에 `upgrade-insecure-requests`, DSN이 있으면 `report-uri https://o….ingest….sentry.io/api/<프로젝트>/security/?sentry_key=…&sentry_environment=preview`와 `Reporting-Endpoints: csp="…"`
   - `Strict-Transport-Security`가 **한 번만** 나옴(Vercel이 붙임, 앱은 붙이지 않음). 없으면 `src/lib/security/csp.ts`의 `COMMON_SECURITY_HEADERS`에 추가 검토
   - `/`는 `x-vercel-cache: HIT`(두 번째 요청부터)가 유지되어야 함(정적 유지 확인). `/notice`는 `MISS`/캐시 없음이 정상
2. [ ] 브라우저(Chrome 시크릿 창, 확장 프로그램 끔) 개발자 도구 Console을 연 채로 아래 화면을 열고 **`Content Security Policy` / `Refused to …` 메시지가 0개**인지 확인
   - 랜딩 `/` → "공지사항" → 공지 하나 열기 → 뒤로
   - "로그인" → Google 로그인 화면으로 넘어감(외부 이동은 CSP와 무관) → 로그인 완료 후 `/world`
   - 월드맵 → 퀘스트 1-1: 코드 실행(`print("안녕하세요!")`) → 정답 → 축하 연출·컨페티(컨페티 Worker는 `blob:`)
   - 튜터 힌트(스트리밍) · 프로필 · 설정 · 게시판 목록·글 보기·댓글 쓰기 · 없는 주소(`/nope`, "길을 찾을 수 없어요")
   - Sentry 확인(DSN이 있을 때): 콘솔에서 `setTimeout(() => { throw new Error('csp smoke') })` → Network에 `ingest…sentry.io` 요청이 막히지 않고 나감 → Sentry Issues에 도착
3. [ ] Pyodide 실행기 경계: 퀘스트 화면에서 아래 코드를 실행하면 `EvalError`(Chrome: `Evaluating a string as JavaScript violates … Content Security Policy`, Firefox: `call to Function() blocked by CSP`)가 나와야 함
   ```python
   import sys
   f = sys.modules["pyodide.webloop"].scheduleCallback
   print(f.constructor("return globalThis")())
   ```
   `[object …]`가 출력되면 Worker CSP가 빠진 것 → Production으로 승격하지 않음
4. [ ] Sentry → Issues에 CSP 이벤트(`csp` 타입)가 새로 생기지 않았는지(DSN이 있을 때)

### Production에서

- [ ] Preview와 같은 1~4를 반복(주소만 Production). 첫 하루는 Sentry의 CSP 이벤트를 하루 한 번 확인: 확장 프로그램·번역기가 아닌 우리 출처(`'self'`, `*.supabase.co`, `cdn.jsdelivr.net`)의 위반이 있으면 원인을 고침

### 비상 전환: Report-Only (화면이 깨질 때)

증상: 버튼이 눌리지 않음·화면이 비어 있음 + 콘솔에 `Refused to execute …` / `Refused to load …`.

1. 바로: Vercel → Deployments에서 직전 배포로 **Instant Rollback** (가장 빠름), 또는
2. Vercel env `CSP_REPORT_ONLY=true`(Production) → 재배포. 페이지 CSP가 `Content-Security-Policy-Report-Only`가 되어 막지 않고 Sentry로 보고만 함. **Worker CSP는 그대로 강제**(eval 경계 유지)
3. Sentry의 CSP 이벤트(또는 콘솔)에서 막힌 출처·지시어를 찾아 `src/lib/security/csp.ts`를 고치고 단위 테스트 추가 → Preview에서 위 확인 → `CSP_REPORT_ONLY` env 삭제 → 재배포(강제로 복귀)

### 새 화면·외부 서비스를 붙일 때 (개발 메모)

- 새 페이지가 빌드 때 정적 HTML로 굳으면 `npm run build`의 postbuild(`scripts/security/check-static-pages.ts`)가 실패함: 동적 렌더로 바꾸거나(로그인 화면·사용자 콘텐츠), 사용자 콘텐츠가 없는 공개 페이지만 `STATIC_PAGE_PATHS`에 넣음
- 외부 출처(분석·이미지 CDN 등)를 붙이면 `buildPageCsp`의 해당 지시어와 테스트를 함께 고침. `'unsafe-eval'`이 필요한 라이브러리는 쓰지 않음(lottie-web은 expression이 있는 애니메이션만 eval을 씀)
- P11-01의 Service Worker(`/pyodide/runner/sw.js`)도 자기 응답의 CSP를 쓰므로 Worker와 같은 정책을 `next.config.ts`에 붙임

### ①을 적용하지 않은 DB에서 새 앱은

- 월드맵·프로필의 `users` 조회(`user_public_profiles(public_name, avatar_skin)` 임베딩)와 게시판 조회(`user_profiles_public(display_name, avatar_skin)`)가 **`avatar_skin` 컬럼이 없어 400(PGRST)으로 실패**합니다: 월드맵 요약 카드가 빠지고, 프로필은 첫 화면으로 돌아가고, 게시판 목록이 비어 보입니다. **반드시 ①을 먼저** 적용합니다. 병합 뒤에 알았다면 ①을 그때 적용하면 되고 재배포는 필요 없습니다(필요하면 `NOTIFY pgrst, 'reload schema';`)
