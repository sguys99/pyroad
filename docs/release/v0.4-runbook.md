# v0.4 릴리즈 런북 (Phase 1 운영 적용)

> - 대상: `feat/phase1` → `main` 병합 때 운영 Supabase와 Vercel에 적용하는 사람(프로젝트 관리자)
> - 원칙: §12-Q21. 마이그레이션은 로컬과 `npm run test:rls:ci`(운영 재현 시나리오 `prod_replay`)로 검증을 마쳤고, 운영 적용은 사람이 SQL Editor에서 합니다. MCP로는 적용하지 않습니다.
> - 순서: **① 추가형 마이그레이션 → ② 앱 배포 → ③ 권한 회수 마이그레이션.** 새 앱은 ①만 적용된 DB와 ①+③ DB 모두에서 동작하고, 이전 앱은 ①만 적용된 DB에서 동작합니다.
> - 각 SQL 파일은 SQL Editor에서 `BEGIN;` + 파일 내용 + `COMMIT;`으로 감싸 실행합니다. 자기 검증 NOTICE가 기대값과 다르면 `ROLLBACK;`하고 멈춥니다.

작업이 끝날 때마다 이 문서에 단계를 추가합니다. 체크박스는 운영 적용 당일에 채웁니다.

## 튜터 한도·남용 기록 (운영, P1-19)

튜터 API(`/api/tutor`, `/api/tutor/stream`)는 사용자마다 요청 유형별로 **분당 / 하루(KST 자정 기준)** 한도를 DB(`api_rate_limits`, `consume_rate_limit`)로 셉니다. 넘으면 429 + `Retry-After`이고 아이에게는 "파이뱀 선생님이 잠깐 쉬고 있어요. N초 뒤에 다시 물어봐요!"(하루 한도는 "내일 다시")가 기준 문구입니다(지금 퀘스트 화면은 기존 실패 문구를 보여 주고 힌트 횟수는 되돌림). 서버 무료 티어 키(Gemini)는 프로젝트 전체가 함께 쓰는 한도라 한 사람이 다 쓰지 못하게 하는 장치입니다.

| env (Vercel, 서버 전용) | 기본값 (분당/하루) | 요청 유형 | 근거 (정상 학습 속도) |
|---|---|---|---|
| `TUTOR_LIMIT_INTRO` | `8/60` | 퀘스트 소개 `quest_intro` | 퀘스트에 들어갈 때 1번 |
| `TUTOR_LIMIT_HINT` | `6/60` | 힌트 `hint_generator` | 단계마다 최대 3번(프로젝트는 단계마다 다시 3번) |
| `TUTOR_LIMIT_FEEDBACK` | `12/200` | 실행 결과 피드백 `code_feedback` | 실행마다 1번. 5초마다 실행해도 통과 |
| `TUTOR_LIMIT_ENCOURAGEMENT` | `4/40` | 완료 격려 `encouragement` | 완료마다 1번 |
| `TUTOR_LIMIT_GUIDE` | `6/40` | 프로젝트 단계 안내 `project_guide` | 단계에 들어갈 때 1번 |
| `TUTOR_LIMIT_SUMMARY` | `3/20` | 스테이지 정리 `stage_summary` | 스테이지 클리어 때 1번 |
| `TUTOR_LIMIT_OWN_KEY_MULTIPLIER` | `2/5` | 본인 API 키 사용자의 배수 | LLM 비용은 본인 부담이라 하루는 ×5, 분당은 서버 부하용이라 ×2 |

- 형식이 틀린 값은 무시하고 기본값을 씁니다(로그 `[tutor] TUTOR_LIMIT_… 형식이 잘못됨`). 바꾼 뒤에는 재배포해야 적용됩니다. 캐시 적중(`quest_intro`·`stage_summary`)도 한도에 셉니다(캐시가 인스턴스마다 따로라 적중 여부로 한도가 달라지지 않게).
- 한도 DB 호출이 실패하면 **통과시킵니다**(fail-open, 튜터를 멈추지 않음). 로그 `[tutor] consume_rate_limit 실패` + Sentry `area:tutor op:rate_limit`.
- 수업 시간에 정상 사용이 막힌다는 제보가 있으면 아래 2번 쿼리로 확인하고 env를 올립니다. 한도를 끄는 스위치는 없습니다(아주 큰 값, 예: `1000/10000`).

**비정상 요청 기록**: Vercel 로그에서 `[tutor-abuse]`로 찾습니다. 한 줄이 JSON `{"event":"tutor_abuse","level","reason","kind","user":<사용자 해시 16자>, …}`이고 학생 코드·출력·질문은 들어 있지 않습니다.

| reason | 뜻 | 수준 |
|---|---|---|
| `rate_limited` | 한도 초과 (`scope` minute/day, `denied_minute`·`denied_today`) | info. 같은 분 창에 5번 이상 또는 하루 100번 이상이면 warning |
| `invalid_json`·`invalid_type`·`missing_quest_id`·`invalid_hint_level`·`missing_execution_result` | 우리 화면은 보내지 않는 형식 (직접 만든 요청) | warning |
| `body_too_large` | 본문 64KB 초과 (413, 읽지 않음) | warning |
| `quest_not_found` | 없는 퀘스트 id (`quest_id`는 UUID일 때만 남김) | warning |
| `input_too_long` | 길이 제한을 넘어 잘라서 처리 (`fields`에 필드 이름만) | info |
| `stage_locked` | 잠긴 스테이지의 퀘스트에 튜터 호출 (막지 않음: 퀘스트 화면이 아직 잠금을 확인하지 않음) | info |

- warning은 Sentry 메시지 `tutor abuse: <reason>`으로도 갑니다(사유별 한 이슈, 인스턴스마다 10분 3번까지. 사용자 해시는 Sentry에 보내지 않음 — P1-16 최소 수집). 한 사유가 갑자기 늘면 Vercel 로그에서 같은 시간대의 `user` 해시를 봅니다.

```sql
-- 1. 로그의 사용자 해시 → 사용자 (해시 = sha256(user id) 앞 16자)
select id, created_at, last_login_at from public.users
 where left(encode(sha256(convert_to(id::text, 'UTF8')), 'hex'), 16) = '<해시>';

-- 2. 오늘(KST) 한도에 걸린 사용자·유형 (카운터는 최근 2일치만 남음)
select left(encode(sha256(convert_to(user_id::text, 'UTF8')), 'hex'), 16) as user_hash, bucket,
       day_count, day_denied, updated_at
  from public.api_rate_limits
 where day = public.kst_today() and day_denied > 0
 order by day_denied desc limit 20;

-- 3. 오늘 많이 쓴 사용자 (정상 사용량 확인, 한도 조정 근거)
select bucket, count(*) as users, max(day_count) as max_count,
       percentile_cont(0.9) within group (order by day_count) as p90
  from public.api_rate_limits where day = public.kst_today() group by 1 order by 1;

-- 4. 특정 사용자의 오늘 한도 풀기 (잘못 막혔을 때)
delete from public.api_rate_limits where user_id = '<id>' and bucket = 'tutor:<유형>';
```

## 관리자 role 설정 (운영, B37)

새 앱은 관리자를 `app_metadata.role = 'admin'`으로 판별하고(`src/lib/admin.ts`), 이행 기간에만 `ADMIN_EMAIL`과 같은 **확인된** 이메일을 폴백으로 인정합니다. `app_metadata`(DB `raw_app_meta_data`)는 service_role·postgres만 바꿀 수 있습니다. `user_metadata`(`raw_user_meta_data`)는 사용자가 직접 바꿀 수 있으므로 **절대 여기에 role을 넣지 않습니다.** 이전 앱은 role을 보지 않으므로 ① 전이든 ② 뒤든 언제 해도 되고, 마이그레이션 파일은 없습니다. SQL Editor(postgres)에서 실행합니다.

```sql
-- 1. 확인 (읽기 전용): 관리자 계정 찾기 — Vercel env ADMIN_EMAIL 값으로
select u.id, u.email, u.email_confirmed_at is not null as email_confirmed,
       u.raw_app_meta_data ->> 'role' as role,
       array_agg(i.provider order by i.created_at) as identities, u.last_sign_in_at
  from auth.users u
  left join auth.identities i on i.user_id = u.id
 where lower(u.email) = lower('<ADMIN_EMAIL 값>')
 group by u.id;
-- 기대: 1행, email_confirmed = true, role = NULL(아직 설정 전). 2행 이상이거나 0행이면 멈추고 확인

-- 지금 role = admin 인 계정 전체 (설정 전에는 0행, 설정 뒤에는 의도한 계정만)
select id, email, raw_app_meta_data ->> 'role' as role, last_sign_in_at
  from auth.users where raw_app_meta_data ->> 'role' = 'admin';

-- 2. 설정: 1번에서 확인한 id 하나만
begin;
update auth.users
   set raw_app_meta_data = coalesce(raw_app_meta_data, '{}'::jsonb) || '{"role":"admin"}'::jsonb
 where id = '<관리자 id>';
-- 기대: UPDATE 1. 아니면 rollback;
select id, email, raw_app_meta_data from auth.users where id = '<관리자 id>';
-- 기대: 기존 provider·providers 키가 그대로 있고 "role": "admin" 이 더해짐
commit;

-- 회수 (관리자를 바꾸거나 잘못 넣었을 때)
update auth.users set raw_app_meta_data = raw_app_meta_data - 'role' where id = '<id>';
```

- 앱은 요청마다 `auth.getUser()`로 Auth 서버에서 사용자를 새로 읽으므로 **다시 로그인하지 않아도 바로 반영**됩니다(브라우저 JWT의 `app_metadata`는 토큰 갱신 전까지 예전 값이지만 판별에 쓰지 않음).
- 확인: 관리자 계정으로 `/notice` → "공지 작성" 버튼이 보임. role만으로 되는지까지 보려면 로컬이나 Preview에서 `ADMIN_EMAIL`을 비우고 같은 계정으로 확인합니다.
- Kakao·Naver로 들어오는 관리자는 이메일이 없으므로(§2.8) role로만 관리자가 됩니다. id는 `select user_id from auth.identities where provider = 'kakao' and provider_id = '<회원번호>';`처럼 identity로 찾습니다.
- **폴백 제거 (다음 릴리즈)**: 위 설정과 확인을 마친 뒤 `src/lib/admin.ts`의 `TODO(B37)` 폴백과 `.env.example`·Vercel의 `ADMIN_EMAIL`을 지웁니다. 그 전에 2번의 "role = admin 계정 전체" 쿼리가 의도한 계정을 돌려주는지 다시 확인합니다.

## 적용 뒤 정리 (별도 커밋)

v0.4를 운영에 적용하고 확인한 **다음 배포**에서 합니다. v0.4 앱은 ①만 적용된 DB에서도 동작해야 해서(§12-Q21) `quests.expected_output`을 아직 읽으므로, 같은 릴리즈에서 컬럼을 지우면 v0.4 앱이 깨집니다. 그래서 P1-12에서는 이 마이그레이션을 **만들지 않았습니다**(`supabase/migrations/`에 두면 `db reset`·CI가 바로 적용해 지금 앱의 채점이 깨짐).

1. 앱 커밋 (그 릴리즈의 ②): `src/lib/quest/answerKeys.ts`의 `quests` 폴백(`LegacyAnswerSource`)·`stripAnswerFields`, `src/lib/quest/grade.ts`의 `quests.expected_output` select 제거(`src/app/api/tutor/helpers.ts`는 `select('*')`라 폴백 인자만 정리, `src/lib/types/database.ts`의 `Omit` 주석도). `src/lib/content/build.ts`의 seed가 `quests.expected_output`을 쓰지 않게(컬럼 기본값 `''`이라 컬럼이 있는 DB에서도 동작) 바꾸고 `supabase/seed.sql` 다시 생성
2. 마이그레이션 `000NN_drop_quests_answer_split.sql` (**릴리즈 단계: ③** — README 표의 "컬럼·폴백 삭제", 새 앱 배포 뒤. `run.sh`가 ③ 파일을 ① 뒤에 적용하므로 별도 단계 표기는 필요 없음):

   - 되돌리기 파일(`rollback/`)은 컬럼(`DEFAULT ''`)·트리거·CHECK 복원
   - `npm run db:types`로 타입 재생성, 회귀 테스트의 `B07-2`(`quests.expected_output`) 점검을 "컬럼 없음"으로 바꿈
