> - v0.5 = Phase 2·4·5·6(§10). **Phase마다 `main`에 병합하면 Vercel이 바로 운영 배포**하므로 병합 단위로 절을 나눕니다. 이 문서는 "Phase 2 병합"으로 시작하고 Phase 4~6이 끝날 때마다 아래에 같은 형식의 절을 덧붙입니다. 태그 `v0.5`는 Phase 6까지 병합한 뒤 `main`에서 붙입니다
> - 원칙은 [v0.4 런북](v0.4-runbook.md)과 같습니다(§12-Q21): 마이그레이션은 로컬과 `npm run test:rls:ci`(운영 재현 `prod_replay`)로 검증했고, 운영 적용은 사람이 SQL Editor에서 합니다. MCP로는 적용하지 않습니다. 순서는 **① 추가형 마이그레이션 → ② 병합·배포 → ③ 권한 회수 마이그레이션**(있을 때만)
> - **SQL은 `release-sql` 묶음 파일로 붙여 넣습니다**(B39, Windows 붙여넣기는 줄바꿈이 CRLF로 바뀜): `node scripts/release/build-release-sql.mjs --release <릴리즈>` → 저장소의 `release-sql/<릴리즈>/`(git 제외). 각 파일 안에 `BEGIN;`/`COMMIT;`이 있어 파일 전체를 그대로 붙여 실행하고, 하나라도 실패하면 그 파일 전체가 되돌려집니다. CRLF 리허설: `RLS_CRLF=1 RLS_SKIP_NEWDEFAULT=1 npm run test:rls:ci`(v0.4 묶음부터 모든 릴리즈 묶음을 CRLF로 바꿔 운영 재현 DB에 순서대로 적용, 점검 CR-1~4)

체크박스는 운영 적용 당일에 채웁니다.

### ① 추가형 마이그레이션 (병합 전)

`release-sql/v0.5-phase2/1_먼저실행.sql` 전체를 SQL Editor에 붙여 실행합니다. 지금 운영 중인 v0.4 앱은 이 함수를 쓰지 않으므로 **병합 전 언제 적용해도 이전 앱은 그대로 동작**합니다.

| 순서 | 파일 | 작업 ID | 확인 |
|---|---|---|---|
| 1 | `supabase/migrations/00020_patch_user_settings.sql` | P2-14 (P2-15 이월) | NOTICE `[00020] patch_user_settings: anon/authenticated 실행 불가`(anon/authenticated가 실행할 수 있거나 service_role이 못 하면 예외로 롤백). 새 함수 하나(`settings = settings \|\| p_patch` 한 문장, 키는 `motion`·`sound`만, SECURITY INVOKER + `search_path` 고정)만 만들고 테이블·권한은 바꾸지 않음. 아래 "00020 확인" |

#### 00020 확인 (P2-14)

- 함수와 권한 (anon·authenticated `f`, service_role `t`)
  ```sql
  select p.oid::regprocedure as fn, p.prosecdef as security_definer, p.proconfig,
         has_function_privilege('anon', p.oid, 'EXECUTE')          as anon,
         has_function_privilege('authenticated', p.oid, 'EXECUTE') as auth,
         has_function_privilege('service_role', p.oid, 'EXECUTE')  as svc
    from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'public' and p.proname = 'patch_user_settings';
  -- 1행: fn = patch_user_settings(uuid,jsonb), security_definer = false, proconfig 에 search_path="", anon = false, auth = false, svc = true
  ```
- 동작 (데이터를 바꾸지 않음: 없는 사용자 id)
  ```sql
  select public.patch_user_settings('00000000-0000-0000-0000-000000000000', '{"motion": {}}'::jsonb);  -- false (바꾼 행 없음)
  select public.patch_user_settings('00000000-0000-0000-0000-000000000000', '{"coins": {}}'::jsonb);   -- 오류 invalid_settings_key
  ```
- API가 함수를 찾는지는 ②의 설정 저장으로 확인합니다. Supabase는 DDL 뒤 API 스키마 캐시를 자동으로 새로 고치지만, ② 뒤 Vercel 로그에 `[settings] patch settings 실패: PGRST202`가 보이면 SQL Editor에서 `NOTIFY pgrst, 'reload schema';`를 한 번 실행합니다

- 테이블·정책·함수 권한
  ```sql
  select has_table_privilege('anon', 'public.user_seen_unlocks', 'SELECT')          as anon_read,    -- false
         has_table_privilege('authenticated', 'public.user_seen_unlocks', 'SELECT') as auth_read,    -- true
         has_table_privilege('authenticated', 'public.user_seen_unlocks', 'INSERT') as auth_write,   -- false
         (select relrowsecurity from pg_class where oid = 'public.user_seen_unlocks'::regclass) as rls; -- true

  select p.oid::regprocedure as fn, p.prosecdef as security_definer, p.proconfig,
         has_function_privilege('anon', p.oid, 'EXECUTE')          as anon,
         has_function_privilege('authenticated', p.oid, 'EXECUTE') as auth,
         has_function_privilege('service_role', p.oid, 'EXECUTE')  as svc

   where n.nspname = 'public' and p.proname = 'record_seen_unlocks';
  ```
