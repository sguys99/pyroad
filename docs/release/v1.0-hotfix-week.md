## 3. 핫픽스 절차

규칙: CLAUDE.md "브랜치 & 커밋 규칙"·계획서 §2.7 — `main`에서 `hotfix/<주제>`, 커밋 `<이모지> fix: <요약> (B<번호>)`(긴급 수정 이모지는 기존 핫픽스처럼 `🚑️`, 보안은 `🔒️`), PR은 필수 체크 통과 뒤 **Merge commit**(squash 금지), 병합 뒤 진행 중인 브랜치에 `main` 반영.

### 3-1. 앱만 고칠 때

```bash
# 0) B 번호: 계획서의 가장 큰 B 번호 + 1
grep -o '\*\*B[0-9]*\*\*' docs/4.upgrade-plan.md | tr -dc '0-9\n' | sort -n | tail -1

# 1) 분기
git fetch origin && git switch main && git pull --ff-only
git switch -c hotfix/<주제>            # 예: hotfix/quiz-complete-500

# 2) 고치고 회귀 테스트를 같은 커밋에 (재현 테스트가 먼저 실패하는 것을 확인)
npm run lint && npx prettier --check . && npx tsc --noEmit && npx vitest run
#    해당되면: npm run test:content · npm run test:rls:ci · npm run test:e2e -- <스펙>

# 3) 커밋 — 바꾼 파일만 add (git add -A 금지)
git add <바꾼 파일들>
git commit -m "🚑️ fix: <무엇을 고쳤나 한 줄> (B<번호>)"
#    계획서 기록은 같은 커밋 또는 바로 다음 커밋: Phase 12 버그 목록에 B 줄 · 상태표 "+ 버그" 수 · §13 한 줄
git add docs/4.upgrade-plan.md
git commit -m "📝 docs: <요약> 기록 (B<번호>)"
git push -u origin hotfix/<주제>

# 4) PR → 필수 체크 → Merge commit
gh pr create --base main --title "🚑️ fix: <요약> (B<번호>)" --body "<무엇이 · 영향 · 원인 · 고친 것 · 회귀 테스트 · DB 변경 없음>"
gh pr checks --watch
gh pr merge --merge --delete-branch

# 5) 배포 확인: Vercel Production 배포 성공 → 그 증상을 직접 재현해 봄 → 1절 ①·③
# 6) 태그 — 3-2 패치 버전 규칙을 사용자가 정한 뒤에만 (CLAUDE.md: v1.0.x 규칙 미정, 임의로 만들지 않음). main 에서
git fetch origin && git switch main && git pull --ff-only
git log --oneline -1                   # "Merge pull request #… from sguys99/hotfix/<주제>" 인지
git tag -a v1.0.1 -m "pyRoad v1.0.1 - <요약> (B<번호>)"
git push origin v1.0.1

# 7) 진행 중인 브랜치가 있으면 (예: v1.1 작업)
git switch <브랜치> && git merge main && git push
```

- 학생이 알아챌 만큼 오래 막혔던 것(로그인·진행·개인정보)은 **공지**: 관리자로 `/notice` → "공지 작성". 문구는 4절 응대 문구를 짧게
- 사고 기록(4절)의 "조치"에 PR 번호·태그를 적음

### 3-2. 패치 버전 (제안 — 사용자 결정 대기)

지금 규칙은 마일스톤 태그(v0.4~v1.0)뿐이고 런북은 `v1.0.0`을 붙입니다. CLAUDE.md는 "v1.0 이후 패치 태그(v1.0.x) 규칙은 아직 정하지 않았다 — 임의로 만들지 말고 사용자에게 묻는다"고 적고 있으므로, 아래는 **제안**입니다(정해지면 CLAUDE.md "Pull Request & 릴리즈"·계획서 §2.7에 한 줄, 그 전에는 태그 없이 PR 번호로만 기록):

- 운영 앱이나 DB를 바꾸는 핫픽스가 `main`에 병합되면 그 병합 커밋에 `v1.0.N`(N = 1, 2, …) 주석 태그
- 같은 날 여러 핫픽스는 마지막 병합에 하나만, 문서만 바뀐 병합은 태그 없음
- 새 기능·v1.1 후보는 `v1.1.0`(다음 마일스톤)
- 푸시한 태그는 지우고 다시 붙이지 않음(런북 2-10과 같음). README 버전 배지(P12-10)가 있으면 같은 핫픽스 PR에서 숫자를 올림

### 3-3. DB 변경이 필요한 핫픽스

될 수 있으면 앱만으로 고칩니다. DB가 필요하면:

1. `supabase/migrations/000NN_<설명>.sql` — 다음 번호(v1.0 끝 = 00062), 멱등, **① 추가형만**(권한 회수 ③을 섞지 않음), 머리 주석·GRANT/REVOKE·NOTICE·자기 검증은 CLAUDE.md "마이그레이션"대로. 되돌리기 `supabase/rollback/000NN_….rollback.sql`
2. `npm run db:reset && npm run db:types && npx tsc --noEmit`, 권한이 바뀌면 `npm run test:rls` + `supabase/tests/expectations.mjs` 갱신, 마지막으로 `RLS_CRLF=1 npm run test:rls:ci`
3. `scripts/release/build-release-sql.mjs`의 `RELEASES`에 새 묶음 `{ name: 'v1.0.N-hotfix', dir: 'v1.0.N-hotfix', bundles: [{ file: '1_먼저실행.sql', stage: 1, head: [...], setup: ["SET LOCAL lock_timeout = '10s';"], parts: ['000NN'] }] }`(v1.0 묶음과 같은 꼴)
4. 운영 적용은 **v1.0 런북을 줄여서**, PR 병합 **전에**: 0-1 관리자 role은 생략 · 0-2 대신 "새 객체가 아직 없음" 한 줄 확인 → 1-3 적용 전 스냅샷 → 묶음 붙여 실행·NOTICE 확인 → 2-2 적용 후 스냅샷 비교 → PR 병합·배포 → 그 증상 스모크. 백업(1-2 `pg_dump`)은 데이터를 바꾸는 마이그레이션일 때만 필수. 이 순서와 기대 NOTICE·되돌리기 SQL을 PR 본문에 적음(별도 런북 파일은 만들지 않음)
5. 묶음 이름·적용 날짜를 계획서 §13 줄에
