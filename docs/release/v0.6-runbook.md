# v0.6 릴리즈 런북 (Phase 7·8 운영 적용)

> - 대상: `feat/phaseN` → `main` 병합 때 운영 Supabase와 Vercel에 적용하는 사람(프로젝트 관리자)
> - v0.6 = Phase 7·8(§10). Phase마다 `main`에 병합하면 Vercel이 바로 운영 배포하므로 병합 단위로 절을 나눕니다. 이 문서는 "Phase 7 병합"으로 시작하고 Phase 8이 끝나면 아래에 같은 형식의 절을 덧붙입니다. 태그 `v0.6`은 Phase 8까지 병합한 뒤 `main`에서 붙입니다
> - 원칙은 [v0.4 런북](v0.4-runbook.md)·[v0.5 런북](v0.5-runbook.md)과 같습니다(§12-Q21): 마이그레이션은 로컬과 `npm run test:rls:ci`(운영 재현 `prod_replay`)로 검증했고, 운영 적용은 사람이 SQL Editor에서 합니다. MCP로는 적용하지 않습니다. 순서는 **① 추가형 마이그레이션 → ② 병합·배포 → ③ 권한 회수 마이그레이션**(있을 때만)
> - **SQL은 `release-sql` 묶음 파일로 붙여 넣습니다**(B39): `node scripts/release/build-release-sql.mjs --release <릴리즈>` → `release-sql/<릴리즈>/`(git 제외). 파일 안에 `BEGIN;`/`COMMIT;`이 있어 전체를 그대로 붙여 실행하고, 하나라도 실패하면 전체가 되돌려집니다. CRLF 리허설: `RLS_CRLF=1 RLS_SKIP_NEWDEFAULT=1 npm run test:rls:ci`

체크박스는 운영 적용 당일에 채웁니다.

#### 00026 확인 (P7-02)

- 함수와 권한 (anon·authenticated `f`, service_role `t`)
  ```sql
  select p.oid::regprocedure as fn, p.prosecdef as security_definer,
         has_function_privilege('anon', p.oid, 'EXECUTE')          as anon,
         has_function_privilege('authenticated', p.oid, 'EXECUTE') as auth,
         has_function_privilege('service_role', p.oid, 'EXECUTE')  as svc
    from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'public' and p.proname in ('submit_quiz_answer', 'is_stage_unlocked', 'complete_quest', 'reset_progress');
  -- 4행: anon = false, auth = false, svc = true. is_stage_unlocked 말고는 security_definer = true (reset_progress 는 00027, B50)
  ```
- 동작 (데이터를 바꾸지 않음: 없는 퀘스트 id)
  ```sql
  select public.submit_quiz_answer('00000000-0000-0000-0000-000000000000', '00000000-0000-0000-0000-000000000000', '"x"');
  -- 오류 quest_not_found
  ```

#### 00029 사전 점검 (P8-02, 적용 전 운영에서 읽기 전용)

새 곡선은 낮은 레벨 문턱이 높아서(Lv 2 = 100 → 200, Lv 3 = 300 → 490, Lv 4 = 600 → 830, Lv 5 = 1,000 → 1,210 XP) 그대로 두면 일부 사용자 레벨이 **내려갑니다**. 00029는 그런 사용자의 `total_xp`를 새 곡선에서 **같은 레벨의 문턱까지 올려** 레벨을 지킵니다(레벨은 그대로, 다음 레벨까지 남은 XP만 늘어남, 한 사람 최대 +230 XP). 예전 레벨은 `min(current_level, 옛 곡선(total_xp))`(옛 앱이 `current_level`을 직접 쓸 수 있던 B04 대비). 1,620 XP 이상은 Lv 6 이상으로 오릅니다. Supabase MCP나 SQL Editor에서 **00028 적용 전에** 실행해 영향 사용자 수를 봅니다:

```sql
-- ① 예전 레벨별: 사용자 수 · XP 보정 대상 수 · 보정 XP 합 (00029 와 같은 식)
with u as (
  select total_xp,
         greatest(1, least(current_level, (select count(*)::int from unnest(array[0, 100, 300, 600, 1000]) t(x) where total_xp >= t.x))) as lv
    from public.users)
select lv as level_before, count(*) as users,
       count(*) filter (where total_xp < (array[0, 200, 490, 830, 1210])[lv]) as bumped,
       coalesce(sum((array[0, 200, 490, 830, 1210])[lv] - total_xp) filter (where total_xp < (array[0, 200, 490, 830, 1210])[lv]), 0) as xp_added
  from u group by lv order by lv;
-- ② 새 곡선에서 오르는 사용자 (Lv 6 이상) · current_level 이 옛 곡선과 다른 사용자 (옛 앱 직접 쓰기 흔적)
select count(*) filter (where total_xp >= 1620) as level_up,
       count(*) filter (where current_level <> greatest(1, (select count(*)::int from unnest(array[0, 100, 300, 600, 1000]) t(x) where total_xp >= t.x))) as level_mismatch
  from public.users;
-- ③ XP 출처 점검: total_xp 가 퀘스트·퀴즈로 받은 XP 합(earned_xp)과 다른 사용자
with s as (select u.id, u.total_xp, coalesce(sum(p.earned_xp), 0) as earned
             from public.users u left join public.user_progress p on p.user_id = u.id and p.status = 'completed'
            group by u.id, u.total_xp)
select count(*) filter (where total_xp < earned) as below_earned,   -- 이전 리셋 과다 차감 등 (B12 이전)
       count(*) filter (where total_xp > earned) as above_earned,   -- 옛 앱 직접 쓰기(B04) 등
       max(abs(total_xp - earned)) as max_gap
  from s;
```

- ①의 `bumped`가 00029 NOTICE의 "보정 N명"과 같아야 합니다(00028과 00029가 같은 묶음이라 사이에 바뀌는 사용자 없음)
- ③은 **고치지 않습니다**(00029는 `total_xp`를 기준으로 레벨만 지킴). 0이 아니면 수와 `max_gap`을 보고 판단합니다: `below_earned`는 스테이지 리셋 한 번이면 earned_xp 합으로 맞춰지고(B12), `above_earned`를 earned_xp 합으로 내리면 레벨이 내려가므로 그대로 두는 것을 권장. 00029 뒤에 다시 볼 때는 보정분을 더해 비교: `earned + coalesce((select xp_after - xp_before from public.level_curve_adjustments a where a.user_id = s.id), 0)`
- 알아 둘 것: 보정 XP는 `earned_xp`에 없습니다. 같은 묶음의 00030(B55) 뒤로는 스테이지 리셋이 **지운 진행의 earned_xp만** 빼므로 보정분이 남습니다(전체 리셋은 0). 그래서 ③의 `below_earned`도 이제 스테이지 리셋으로 earned_xp 합에 맞춰지지 않고 그대로 남습니다

#### 00037 사전 점검 (P8-11, 적용 전 운영에서 읽기 전용 — 00028 적용 전 DB 에서 그대로 돌아감)

소급 대상 수와 지급될 코인 합을 미리 봅니다. 00037 NOTICE 의 숫자와 같아야 합니다(적용 전이라 원장이 비어 있어 "모두 새로 줌" 기준). 레벨은 00029 뒤 레벨 = max(옛 레벨, 새 곡선 레벨).

```sql
-- ① 별 채울 완료(코드·프로젝트) · 퀘스트 코인 · 코드 별 코인 (황금키 완료는 별 1·코인 0)
select count(*)                                                        as fill_rows,
       count(*) filter (where not p.used_golden_key)                   as quest_coin_rows,
       10 * count(*) filter (where not p.used_golden_key)              as quest_coins,
       5 * coalesce(sum(case when p.hints_used = 0 then 3 when p.hints_used = 1 then 2 else 1 end)
                     filter (where not p.used_golden_key), 0)          as code_star_coins
  from public.user_progress p join public.quests q on q.id = p.quest_id
 where p.status = 'completed' and q.quest_type <> 'quiz';
-- ② 퀴즈 별 코인 (00026 이 적은 best_stars)
select 5 * coalesce(sum(least(p.best_stars, 3)), 0) as quiz_star_coins
  from public.user_progress p join public.quests q on q.id = p.quest_id
 where p.status = 'completed' and q.quest_type = 'quiz' and p.best_stars > 0;
-- ③ 레벨 업 코인 (Lv 2..레벨, 5레벨마다 100 나머지 20) · 사용자 분포
with lv as (
  select greatest(
           greatest(1, least(u.current_level, (select count(*)::int from unnest(array[0, 100, 300, 600, 1000]) t(x) where u.total_xp >= t.x))),
           1 + (select count(*)::int from generate_series(2, 50) n where u.total_xp >= round(200 * power(n - 1, 1.3) / 10) * 10)) as level
    from public.users u)
select count(*) filter (where level > 1) as level_users, max(level) as max_level,
       coalesce(sum((select sum(case when n % 5 = 0 then 100 else 20 end) from generate_series(2, level) n)), 0) as level_coins
  from lv;
```
