# v0.6 릴리즈 런북 (Phase 7·8 운영 적용)

> - 대상: `feat/phaseN` → `main` 병합 때 운영 Supabase와 Vercel에 적용하는 사람(프로젝트 관리자)
> - v0.6 = Phase 7·8(§10). Phase마다 `main`에 병합하면 Vercel이 바로 운영 배포하므로 병합 단위로 절을 나눕니다. 이 문서는 "Phase 7 병합"으로 시작하고 Phase 8이 끝나면 아래에 같은 형식의 절을 덧붙입니다. 태그 `v0.6`은 Phase 8까지 병합한 뒤 `main`에서 붙입니다
> - 원칙은 [v0.4 런북](v0.4-runbook.md)·[v0.5 런북](v0.5-runbook.md)과 같습니다(§12-Q21): 마이그레이션은 로컬과 `npm run test:rls:ci`(운영 재현 `prod_replay`)로 검증했고, 운영 적용은 사람이 SQL Editor에서 합니다. MCP로는 적용하지 않습니다. 순서는 **① 추가형 마이그레이션 → ② 병합·배포 → ③ 권한 회수 마이그레이션**(있을 때만)
> - **SQL은 `release-sql` 묶음 파일로 붙여 넣습니다**(B39): `node scripts/release/build-release-sql.mjs --release <릴리즈>` → `release-sql/<릴리즈>/`(git 제외). 파일 안에 `BEGIN;`/`COMMIT;`이 있어 전체를 그대로 붙여 실행하고, 하나라도 실패하면 전체가 되돌려집니다. CRLF 리허설: `RLS_CRLF=1 RLS_SKIP_NEWDEFAULT=1 npm run test:rls:ci`

체크박스는 운영 적용 당일에 채웁니다.

### ① 추가형 마이그레이션 (병합 전)

`release-sql/v0.6-phase7/1_먼저실행.sql` 전체를 SQL Editor에 붙여 실행합니다. 지금 운영 중인 앱은 `submit_quiz_answer`를 부르지 않고, 운영에는 아직 퀴즈 콘텐츠가 없어 `is_stage_unlocked`·`complete_quest`의 결과도 같으므로 **병합 전 언제 적용해도 이전 앱은 그대로 동작**합니다. 00027의 `reset_progress`도 인자·반환이 같아 이전 앱의 진행 초기화가 그대로 동작합니다(퀴즈 시도 기록이 없으면 결과도 같음).

⚠️ 00012·00019 파일 전체를 나중에 다시 실행하면 두 함수가 그 정의로 돌아갑니다(퀴즈가 다시 잠금에 들어감). 다시 실행했다면 00026도 다시 실행합니다. 00006·00012를 다시 실행했다면 00027도 다시 실행합니다(`reset_progress`).

#### 00026 확인 (P7-02)

- 함수와 권한 (anon·authenticated `f`, service_role `t`)
  ```sql
  select p.oid::regprocedure as fn, p.prosecdef as security_definer,
         has_function_privilege('anon', p.oid, 'EXECUTE')          as anon,
         has_function_privilege('authenticated', p.oid, 'EXECUTE') as auth,
         has_function_privilege('service_role', p.oid, 'EXECUTE')  as svc
    from pg_proc p join pg_namespace n on n.oid = p.pronamespace
   where n.nspname = 'public' and p.proname in ('submit_quiz_answer', 'is_stage_unlocked', 'complete_quest', 'reset_progress');
  -- 4행: anon = false, auth = false, svc = true. is_stage_unlocked 말고는 security_definer = true (reset_progress 는 00027, B50)
  ```
- 동작 (데이터를 바꾸지 않음: 없는 퀘스트 id)
  ```sql
  select public.submit_quiz_answer('00000000-0000-0000-0000-000000000000', '00000000-0000-0000-0000-000000000000', '"x"');
  -- 오류 quest_not_found
  ```

### ①을 적용하지 않은 DB에서 새 앱은

- `/api/quest/answer`가 500(`PGRST202`)이라 **퀴즈만 채점되지 않습니다**. 코드 퀘스트·보상은 그대로입니다
- 스테이지 잠금은 서버(00012 `is_stage_unlocked`)가 퀴즈까지 세고 월드맵(TS)은 빼므로, 퀴즈 콘텐츠가 있는 스테이지에서 화면은 열렸는데 퀘스트 페이지가 잠김으로 보일 수 있습니다. 병합 뒤에 알았다면 ①을 그때 적용하면 됩니다(앱 재배포 불필요)

## Phase 8 병합 (레벨·코인·별·미션·업적, 릴리즈 묶음 `v0.6-phase8`)

**바뀌는 것**: 레벨 Lv 1~50 곡선·칭호 50종(P8-01). Phase 8의 다른 작업이 끝나면 이 절에 덧붙입니다.

DB 변경 (Phase 8 진행 중 갱신)

| 순서 | 파일 | 작업 ID | 확인 |
|---|---|---|---|
| 1 | `supabase/migrations/00028_level_curve.sql` | P8-01, B20 | NOTICE `[00028] level_for_xp: 50단계 곡선, users current_level 트리거 확인`. `level_for_xp` 본문 교체(5단계 → Lv 1~50, 문턱 = round(200 × (N − 1)^1.3, 10 단위), 인자·반환·권한 그대로) + 트리거 `trg_users_sync_level`(`current_level := level_for_xp(total_xp)`, B20). **기존 사용자 레벨 재계산은 P8-02** — 그 전까지 `current_level`은 그 사용자의 `total_xp`가 바뀔 때(퀘스트 완료 등) 새 곡선으로 맞춰짐. 이전 앱은 5단계 TS 표로 XP 막대를 그리므로 **병합 직전에** 적용 |

```sql
select tgname from pg_trigger where tgrelid = 'public.users'::regclass and tgname = 'trg_users_sync_level';  -- 1행
```
